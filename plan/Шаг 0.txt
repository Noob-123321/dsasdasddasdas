Цель и обзор
------------
Сделать сервис, который открывается по ссылке, принимает один
пользовательский лицензионный ключ, создаёт защищённую сессию и показывает
портфель Twitch-стримеров с подробной аналитикой.

Пользовательский сценарий:
1. Пользователь открывает `/`.
2. Вводит ключ формата `TVS_` + 128 случайных символов.
3. Сервер проверяет ключ, при необходимости обновляет срок действия по
   административной политике, создаёт HttpOnly-сессию и перенаправляет на
   `/dashboard`.
4. Новый профиль показывает пустой портфель и кнопку «Добавить».
5. В модальном окне пользователь вставляет одну или несколько ссылок на
   Twitch-каналы, разделённых пробелами или переводами строк.
6. Каналы автоматически проверяются, добавляются в профиль и ставятся в
   фоновый мониторинг.
7. В профиле доступны текущие значения, история, портфель, аномалии,
   объяснимый risk score, confidence, CSV/PDF-экспорт и API-ключи `tvs_`.
8. Администратор входит отдельным админским ключом, управляет ключами,
   профилями, списками каналов, сроками действия, аудитом и статистикой
   нагрузки сервера.

Архитектурное решение
----------------------
- Backend: FastAPI, Pydantic, SQLAlchemy 2, Alembic, Uvicorn.
- Database: PostgreSQL. SQLite разрешён только для локальных тестов.
- Фоновый сбор: отдельный процесс `poller`, интервал 60 секунд; тяжёлые
  пересчёты вынесены в worker/aggregation job.
- Frontend: React + TypeScript + Vite, React Router, TanStack Query,
  графики на ECharts или аналогичной библиотеке, собственные CSS tokens.
- Кэш и rate limiting: Redis; PostgreSQL остаётся источником истины.
- Запуск: Docker Compose, reverse proxy с HTTPS, отдельные сервисы API и
  poller.
- Источник Twitch на первой версии: существующий анонимный GQL-клиент,
  скрытый за адаптером. Добавляются probe-проверки полей, graceful
  degradation и точка подключения официального Helix API в будущем.
- Время и даты: UTC; суммы в копейках, если позже появится биллинг.

Ключевые продуктовые решения
----------------------------
- `TVS_` — вход в профиль и административный доступ.
- Формат ключа: `TVS_` плюс ровно 128 случайных URL-safe символов, всего
  132 видимых символа.
- Ключ бессрочный по умолчанию, но админ может задать `expires_at`; срок
  можно изменить после создания.
- Ключ можно посмотреть и скопировать администратору в любой момент.
  Секрет не хранится открытым текстом: для копирования используется
  шифрование, для поиска — отдельный SHA-256 lookup hash.
- Один ключ разрешён на нескольких устройствах.
- Роли не вводятся. Есть только профильные и административные ключи;
  административность задаётся флагом записи, а не отдельной RBAC-системой.
- Ограничения на количество каналов нет.
- Для каждого профиля admin задаёт allowlist каналов или снимает
  ограничение (`unlimited=true`).
- Пользователь может добавлять и удалять каналы из своего портфеля в рамках
  разрешённого списка; это не меняет глобальную настройку ключа.
- API-ключи `tvs_` создаются внутри профиля, наследуют доступ к данным
  родительского `TVS_` и автоматически перестают работать вместе с ним.
  По умолчанию API-ключ даёт read-доступ к портфелю и аналитике; изменение
  профиля и создание ключей выполняются через защищённый профиль/UI.
- В API и UI не используется утверждение «это боты». Главное значение —
  наблюдаемая аномальность и качество данных; решение остаётся за человеком.
- Первая полная версия включает алерты и webhooks, но не включает
  white-label виджет, платёжный биллинг, роли, SSO и chat-message sampler.

Идеи, перенесённые из референсных проектов
--------------------------------------------
Из проекта OpenCode:
- портфель каналов;
- объяснимый risk score;
- фоновая история и предподсчитанные агрегаты;
- API-ключи со scopes/лимитами/квотами;
- алерты и webhooks;
- аудит и защищённые административные операции.

Из проекта Claude:
- автоматический старт наблюдения после первого открытия/добавления канала;
- дедупликация повторяющихся значений;
- отдельная дедупликация по изменениям зрителей и чаттеров;
- сессии стримов с различием `ended_at` и `observed_until`;
- измерительные пороги и probe-скрипты;
- trust/quality score с explanation;
- lifecycle-тесты поллера и остановки процесса.

Фазы и ориентировочные сроки
-----------------------------
Оценки предполагают одного full-stack разработчика с доступом к тестовому
Twitch-трафику и помощью DevOps. Это ориентир, а не обязательство.

- Этап 1 (Шаги 1–3): фундамент, ключи, схема и безопасность — 1,5–2 недели.
- Этап 2 (Шаги 4–5): сбор истории, метрики и объяснимый score — 2–3 недели.
- Этап 3 (Шаги 6–7): профиль, портфель и дашборд — 2–3 недели.
- Этап 4 (Шаги 8–10): API, документация, экспорт и алерты — 2–3 недели.
- Этап 5 (Шаги 11–12): инфраструктура, нагрузочные тесты и релиз — 1–2 недели.

Итого: ориентировочно 8–13 недель для первого полноценного релиза.

Границы первой версии
----------------------
Входит:
- один вход по TVS-ключу без регистрации email;
- административный вход по отдельному TVS-ключу;
- любые публичные Twitch-каналы через allowlist или unlimited-профиль;
- фоновая история, графики, аномалии, score, confidence и explanation;
- CSV/PDF, API v1, API-ключи, аудит, алерты и webhooks;
- адаптивный dashboard и admin UI;
- статистика пользователей и нагрузки сервера.

Не входит:
- платёжная подписка и биллинг;
- роли, команды и enterprise SSO;
- white-label виджет;
- гарантированное определение ботов;
- обнаружение событий короче примерно трёх минут;
- обещание доступности неофициального GQL API.
